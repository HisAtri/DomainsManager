# 刷新调度质量审查

审查基线：`3dc7213`，日期：2026-09-07。范围包括默认检查周期、重启分散、请求端点限流、任务合并，以及相关持久化和迁移。

## 发现与修复

| 优先级 | 问题及影响 | 修复与验证 |
| --- | --- | --- |
| P1 | Worker 与 Scheduler 同时启动，Worker 可能先领取集中积压的自动任务；仅检查域名下一周期时间还会漏掉已排队或过期运行任务。 | Worker 领取前也执行分散；选择条件覆盖遗留自动任务，回收过期租约。启动顺序和两种旧队列状态均有测试。 |
| P1 | 调度领取和成功完成都从当前时间重算周期，限流等待可能把已随机分散的计划重新集中。 | 从持久化计划时间递推，跨过错过的周期；测试延迟两小时和连续两个周期。已有活动任务由原任务继续执行。 |
| P1 | 端点冷却等待消耗失败次数，持续限流会把任务标为失败，并生成失败检查和通知。 | 有明确冷却时间时延期原任务，不消耗失败次数；模拟超过最大重试次数后仍能成功完成。成功后清理旧错误字段。 |
| P1 | RDAP 自动重定向只锁定初始 URL，直连目标的其他查询可继续撞限流。 | 每次 HTTP 请求按实际目标取得共享门锁，包括注册商查询；模拟重定向后 429/503 和另一个域名直连目标，确认无额外上游请求。 |
| P1 | 端点租约固定一分钟，长请求未结束就可能被其他实例重新获取；线程式 WHOIS 在取消后仍可能继续收发。 | 增加带令牌校验的租约续期；WHOIS 使用可取消的异步连接和整个交换过程的超时。验证长请求、取消、超时和过期持有者。 |
| P1 | SQLite 不执行 `FOR UPDATE`，多个 Worker 可能读到同一个待处理任务。 | 领取使用条件更新，只有一个请求获得执行权；8 个并发 Worker 验证。 |
| P1 | SQLite 保存点可能先提交任务行，任务和幂等键不是原子的；实测并发同键请求出现唯一约束错误。 | 按域名保护任务写入，SQLite 在保存点前启动真实写事务；重查幂等键，统一父记录和任务锁定顺序。验证并发同键/不同键，以及写入失败后无孤立任务。 |
| P2 | 排队任务合并会丢弃新的 `force_refresh`，手动刷新还可能等待自动任务的随机延迟。 | 排队任务保留强制标志并集；仅提前从未执行且没有错误的自动任务。运行中任务继续执行，冷却与成功刷新 TTL 保留。 |
| P2 | 旧迁移将重复任务标记失败，但幂等键仍指向这些旧任务。 | 新增后续迁移 `21c5b0e8d9a4`，修复指向仍活动的原任务的关联并保留强制标志。旧迁移不变；带真实旧数据验证升级、降级、再升级和外键完整性。 |
| P2 | 退避先计算巨大指数再取上限，长期限流会溢出；超大 Retry-After 同样可能溢出。 | 退避在增长前饱和到上限；保护日期计算。内存和 SQLite 存储均测试连续 65 次限流。 |
| P2 | 回退错误中的 “not found” 会覆盖结构化限流结果；没有错误文字的 TimeoutError 可能被判为不可重试。 | 明确冷却时间优先决定限流分类，按异常类型识别超时；分别增加回归测试。 |
| P2 | 三份示例环境配置仍为 86400 秒，复制配置会覆盖新的默认值。 | 示例配置统一为 604800 秒；现有用户显式配置不强制改写。 |

在修复过程中另补齐自动任务命中新鲜数据时的周期递推，避免立即再次创建任务。

## 设计与可维护性

保留现有任务队列、数据库端点门锁和活动任务唯一索引，没有引入新的队列服务或调度字段。HTTP 端点规范化和有上限退避各保留一个实现，由需要的组件复用。WHOIS 的解析仍在端点锁内完成，以便将文本限流响应更新为共享冷却；RDAP 的锁放在逐次 HTTP 请求处，避免漏掉重定向目标或重复加锁。

RDAP 逐跳处理使用 HTTPX 的 `response.next_request`，保留重定向次数上限；接口依据见 [HTTPX 官方文档](https://www.python-httpx.org/quickstart/#redirection-and-history)。
